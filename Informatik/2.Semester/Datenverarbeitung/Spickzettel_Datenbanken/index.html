Theorie 1

Relationale Grundlagen & Relationale Algebra

🧠

Das relationale Datenmodell basiert auf der Mengenlehre von E. F. Codd. Daten werden in mathematischen Relationen (Tabellen) organisiert, deren Zeilen Tupel und deren Spalten Attribute darstellen.

Definitionen & Grundoperationen

1.1 · RelationMathematisch eine Teilmenge des kartesischen Produkts von Wertebereichen (Domänen): $R \subseteq S_1 \times S_2 \times \dots \times S_n$. Anschaulich: Eine Tabelle.
1.2 · Tupel & AttributEin Tupel ist ein Element der Relation (eine Tabellenzeile). Ein Attribut ist eine benannte Spalte mit festem Wertebereich (Domäne).
1.3 · Atomarität1. Normalform fordert: Alle Attributwerte müssen atomar (im Kontext nicht weiter sinnvoll zerlegbar) sein.
1.4 · Schema vs. ZustandRelationsschema: Struktur & Metadaten (Spaltennamen, Typen, Constraints – ändert sich selten). Ausprägung / Zustand: Der aktuelle Datenbestand zu einem Zeitpunkt.

Relationale Algebra (Operatoren)

• Selektion ($\sigma$): Filtert Zeilen nach Prädikat → entspricht WHERE.

• Projektion ($\pi$): Wählt Spalten aus und eliminiert Duplikate → entspricht SELECT spalten.

• Kartesisches Produkt ($\times$): Bildet alle Paare aus zwei Relationen.

SQL ist eine deklarative Sprache: Man beschreibt WAS man will, das DBMS entscheidet WIE.
✎ Klausur-Safe: Grundbegriffe
  1. Tabelle: Relation $R$
  2. Zeile: Tupel $t \in R$
  3. Spalte: Attribut $A$
  4. Wertebereich: Domäne $dom(A)$
  5. Projektion $\pi$: Spaltenauswahl
  6. Selektion $\sigma$: Zeilenfilter

Theorie 2

Schlüssel-Hierarchie & Surrogatschlüssel

🧠

Ein zentraler Klausurschwerpunkt ist die formale Unterscheidung von Schlüsseln und die Begründung, warum in der Praxis fast immer künstliche Surrogatschlüssel (IDs) verwendet werden.

Die 4 Schlüsselstufen

2.1 · Super-SchlüsselJede Attributmenge, die ein Tupel in der Relation eindeutig identifiziert. Darf überflüssige Attribute enthalten (z. B. {ID, Nachname, E-Mail}).
2.2 · Schlüsselkandidat (Candidate Key)Ein minimaler Super-Schlüssel: Entfernt man auch nur ein einziges Attribut, geht die Eindeutigkeit verloren (irreduzibel).
2.3 · Primärschlüssel (Primary Key)Ein vom Datenbankentwickler ausgewählter Schlüsselkandidat. Restriktionen: Muss zwingend NOT NULL und UNIQUE sein. Kann aus mehreren Spalten bestehen (zusammengesetzter PK)!
2.4 · Fremdschlüssel (Foreign Key)Ein Attribut (oder eine Attributkombination), das auf den Primärschlüssel einer anderen Tabelle verweist und so Beziehungen abbildet.

Warum künstliche Surrogatschlüssel (IDs)?

In der Klausur wird oft gefragt: „Begründen Sie die Wahl des Primärschlüssels (künstliche ID statt natürlicher Schlüssel wie Name/E-Mail)!"

Die 4 stichhaltigen Argumente:

  1. Änderungsresistenz: Natürliche Schlüssel (Namen, E-Mails) können sich ändern; künstliche IDs bleiben lebenslang unverändert.
  2. Performance: Ein schlanker Integer (4 Bytes) ist extrem schnell vergleichbar und performant bei Indexen und JOIN-Operationen.
  3. Eindeutigkeit bei Duplikaten: Zwei Benutzer können denselben Namen tragen.
  4. Datenschutz (DSGVO): Fremdschlüssel in Log- und Zwischentabellen enthalten keine sensiblen Klardaten.
✎ Klausur-Safe: Mustersatz Primärschlüssel

Warum müssen PKs nicht aus nur einer Spalte bestehen?

Primärschlüssel können zusammengesetzt sein (Composite Key). Typischer Fall: In n:m-Zwischentabellen bilden die beiden Fremdschlüssel zusammen den zusammengesetzten Primärschlüssel.

Theorie 3

Referentielle Integrität & Löschregeln

🧠

Referentielle Integrität stellt sicher, dass Fremdschlüsselverweise zu jedem Zeitpunkt gültig sind und nicht auf gelöschte oder nicht-existente Datensätze verweisen.

Mustersatz & Löschregeln (Klausurklassiker)

3.1 · Warum Foreign Keys explizit im DBMS deklarieren? (2 Pkt) Mustersatz: „Das explizite Festlegen von Fremdschlüsseln erzwingt referentielle Integrität auf Datenbankebene: Das DBMS verhindert ungültige Referenzen (Eintragen nicht-existenter Eltern-IDs) und verhindert Datenwaisen (orphaned records) durch automatisierte Konsistenzprüfungen und Kaskadierregeln."
3.2 · Lösch- & Updateregeln
RegelWirkung beim Löschen/Ändern der Elternzeile (Parent)
CASCADEÄnderung oder Löschung wird automatisch an alle Kindzeilen durchgereicht (Kindzeilen mitlöschen).
SET NULLDie Fremdschlüsselspalte in den Kindzeilen wird auf NULL gesetzt (erfordert, dass FK nullable ist).
RESTRICTDie Löschung der Elternzeile wird sofort mit einem Fehler verweigert, solange Kindzeilen existieren.
NO ACTIONStandard in MariaDB/MySQL; verhält sich wie RESTRICT.

Syntax bei CREATE TABLE

Wird am Ende der Tabellendefinition angegeben:

FOREIGN KEY (lehrer_id) 
    REFERENCES musiklehrer(id)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
✎ Klausur-Safe: Löschregeln

• ON DELETE CASCADE: Kunde wird gelöscht → Alle seine Ausleihen werden mitgelöscht.

• ON DELETE RESTRICT: Kunde kann nicht gelöscht werden, solange er noch Filme ausgeliehen hat!

• ON UPDATE CASCADE: ID des Lehrers ändert sich → Fremdschlüssel in allen Kursen passt sich automatisch an.

Theorie 4

Transaktionen & das ACID-Prinzip

🧠

Eine Transaktion ist eine logische Einheit von Datenbankoperationen. Sie garantiert, dass die Datenbank auch bei Systemabstürzen oder parallelen Zugriffen fehlerfrei bleibt.

Die 4 Säulen von ACID

A · Atomicity (Atomarität)„Alles oder nichts": Eine Transaktion wird entweder vollständig und erfolgreich ausgeführt oder komplett zurückgerollt. Es gibt keine halben Transaktionen.
C · Consistency (Konsistenz)Die Datenbank wechselt von einem gültigen Zustand in einen neuen gültigen Zustand. Alle Integritätsbedingungen (Constraints, Checks, FKs) sind am Ende erfüllt.
I · Isolation (Isolation)Gleichzeitig laufende Transaktionen beeinflussen sich nicht gegenseitig. Das Ergebnis ist dasselbe, als wären sie nacheinander (seriell) ausgeführt worden.
D · Durability (Dauerhaftigkeit)Sobald eine Transaktion mit COMMIT erfolgreich abgeschlossen wurde, bleiben die Daten dauerhaft im System gespeichert – selbst bei unmittelbarem Stromausfall oder Servercrash.

Transaktionssteuerung in SQL

START TRANSACTION;
UPDATE konto SET stand = stand - 100 WHERE id = 1;
UPDATE konto SET stand = stand + 100 WHERE id = 2;
-- Wenn alles fehlerfrei war:
COMMIT;
-- Im Fehlerfall:
ROLLBACK;
✎ Klausur-Safe: ACID Kurzform
  • A: Unteilbar (ganz oder gar nicht)
  • C: Erhält Datenkonsistenz & Regeln
  • I: Nebenläufige Isolation
  • D: Dauerhaft nach Commit gesichert

Theorie 5

Suchbäume & Binäre Bäume

🧠

Datenbanken nutzen Baumstrukturen (B-Bäume, binäre Suchbäume) als Indexe, um Datensätze in logarithmischer Zeit $\mathcal{O}(\log n)$ statt linearem Full-Table-Scan $\mathcal{O}(n)$ zu finden.

Zeichenregeln für Binäre Suchbäume

5.1 · Wurzel & VerzweigungDie 1. Zahl der gegebenen Zahlenfolge wird die Wurzel. Für jede nachfolgende Zahl wandert man von der Wurzel abwärts:
• Ist die neue Zahl kleiner als der aktuelle Knoten → gehe nach links.
• Ist die neue Zahl größer als der aktuelle Knoten → gehe nach rechts.
5.2 · Klausur-Falle: Worst-Case-Szenario Wann entartet ein binärer Suchbaum? → Bei bereits vorsortierten Eingabedaten (aufsteigend oder absteigend, z. B. 10, 20, 30, 40, 50)! Der Baum wird zu einer linearen Kette (Liste) mit katastrophaler Suchzeit $\mathcal{O}(n)$.
5.3 · B-Baum vs. BinärbaumDBMS (wie MariaDB InnoDB) nutzen balancierte B+ Bäume: Knoten haben viele Kinder (hoher Verzweigungsgrad), wodurch die Baumhöhe extrem flach bleibt und wenige Festplattenzugriffe nötig sind.
▸ Zeichenbeispiel: Folge [15, 8, 24, 3, 12, 18, 30]
         [15]
        /    \
      [8]     [24]
     /   \    /   \
   [3]  [12] [18]  [30]
Balancierter Baum: Jeder Suchschritt halbiert die verbleibende Menge ($\mathcal{O}(\log n)$).

Theorie 6

ER-Modellierung (Chen / Krähenfuß) & Tabellenabbildung

🧠

Das Entity-Relationship-Modell (ERM) visualisiert die logische Datenstruktur. In der Klausur muss ein vorgegebenes Szenario (z. B. Streaming-Dienst) modelliert und in relationale Tabellen überführt werden.

Notations-Elemente & Kardinalitäten

6.1 · Chen-ElementeRechteck: Entitätstyp (z. B. Benutzer) | Ellipse: Attribut (PK unterstrichen, z. B. id) | Raute: Beziehung (z. B. erstellt).
6.2 · 1:n TransformationFremdschlüssel wandert IMMER auf die n-Seite! Bsp: Ein Benutzer hat $n$ Playlists → Tabelle playlist erhält Spalte benutzer_id als FK!
6.3 · n:m TransformationBenötigt eine **eigene Verknüpfungstabelle**! Bsp: Playlists und Songs (eine Playlist enthält viele Songs, ein Song ist auf vielen Playlists) → Zwischentabelle playlist_song mit Spalten (playlist_id, song_id). Beide zusammen bilden den zusammengesetzten Primärschlüssel!

Klausurszenario Musik-Streaming

• Benutzer (id, geburtsdatum, email)

• Playlist (id, erstelldatum, benutzer_id) — 1:n zu Benutzer

• Song (id, titel, kuenstler)

• Playlist_Song (playlist_id, song_id) — n:m Zwischentabelle

✎ Klausur-Safe: Relationale Schemata

benutzer(id, geburtsdatum, email)

playlist(id, erstelldatum, benutzer_id ↑ benutzer.id)

song(id, titel, kuenstler)

playlist_song(playlist_id, song_id)

DDL: Tabellen anlegen (CREATE TABLE) & Constraints

🧠

In der Praxisaufgabe 1 muss eine vollständige Datenbank mit Primärschlüsseln, Fremdschlüsseln und Integritätsbedingungen angelegt werden (Musikschul-Aufgabe aus 2026).

Wichtige Datentypen & Constraints

7.1 · DatentypenINT, VARCHAR(n), DECIMAL(10,2) (für Geld), DATE ('YYYY-MM-DD'), DATETIME, BOOLEAN (TINYINT 0/1).
7.2 · ConstraintsPRIMARY KEY, AUTO_INCREMENT, NOT NULL, UNIQUE, DEFAULT wert, CHECK (preis > 0).
▸ Vollständige Musterlösung: Musikschule (Gedächtnisprotokoll)
-- 1. Tabelle ohne Abhängigkeiten zuerst erstellen:
CREATE TABLE musikkurs (
    kurscode VARCHAR(20) PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

-- 2. Musiklehrer mit Auto-Increment und Unique Email:
CREATE TABLE musiklehrer (
    id INT AUTO_INCREMENT PRIMARY KEY,
    vorname VARCHAR(50) NOT NULL,
    nachname VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL UNIQUE
);

-- 3. Funktionen mit Fremdschlüssel und Kaskadierung:
CREATE TABLE funktionen (
    id INT AUTO_INCREMENT PRIMARY KEY,
    bezeichnung VARCHAR(50) NOT NULL,
    musiklehrer_id INT NOT NULL,
    FOREIGN KEY (musiklehrer_id) 
        REFERENCES musiklehrer(id) 
        ON UPDATE CASCADE 
        ON DELETE RESTRICT
);
Reihenfolge-Regel: Tabellen immer so anlegen, dass referenzierte Elterntabellen (z. B. musiklehrer) vor den referenzierenden Kindtabellen (z. B. funktionen) erzeugt werden!

Typische Klausur-Abfragen

SELECT kunde_id, COUNT(*) AS anzahl 
FROM ausleihen

Praxis 5

DML: Multi-Table JOINs über Fremdschlüssel

🧠

JOINs verknüpfen Datensätze aus mehreren Tabellen anhand ihrer Primär- und Fremdschlüsselbeziehungen.

Musteraufgabe aus dem Gedächtnisprotokoll

11.1 · Fragestellung„Den Filmtitel abfragen, den der Kunde mit der id 5 ausgeliehen hat."
▸ SQL-Musterlösung: Multi-Table JOIN
Kompakter 2-Tabellen JOIN (filme und ausleihen)
SELECT f.titel 
FROM filme f 
JOIN ausleihen a ON f.id = a.film_id 
WHERE a.kunde_id = 5;
Vollständiger 3-Tabellen JOIN (inkl. Kundennamen)
SELECT k.vorname, k.nachname, f.titel, a.ausleihdatum 
FROM kunden k 
JOIN ausleihen a ON k.id = a.kunde_id 
JOIN filme f     ON a.film_id = f.id 
WHERE k.id = 5;
Liefert exakt alle Filmtitel von Kunde 5.

INNER JOIN vs. LEFT JOIN

INNER JOIN: Liefert nur Zeilen, die in beiden Tabellen einen Treffer haben. Filme, die nie ausgeliehen wurden, tauchen nicht auf.

LEFT JOIN: Behält alle Zeilen der linken Tabelle, selbst wenn in der rechten Tabelle kein Treffer existiert (Felder werden mit NULL aufgefüllt).

✎ Klausur-Safe: Tabellen-Aliase

Verwende immer kurze Tabellen-Aliase (f für filme, a für ausleihen, k für kunden). Das verhindert Spalten-Namenskonflikte und spart viel Schreibarbeit!

DML: Daten verändern & löschen (UPDATE & DELETE)

🧠

Zum Ändern bestehender Zeilen dient UPDATE, zum Entfernen DELETE FROM. In der Praxisaufgabe müssen gezielte Ausleihdaten aktualisiert und einzelne Einträge gelöscht werden.

Musterlösungen (Gedächtnisprotokoll)

12.1 · Ausleihdatum auf '2026-06-26' setzen 
UPDATE ausleihen 
SET ausleihdatum = '2026-06-26' 
WHERE id = 12; -- Gezielter Zugriff über PK
12.2 · Eintrag mit ID 3 löschen 
DELETE FROM ausleihen 
WHERE id = 3;
LEBENSGEFAHR IN SQL: Ein UPDATE oder DELETE ohne WHERE überschreibt oder vernichtet alle Zeilen der gesamten Tabelle! Prüfe in der Klausur dreimal, ob die WHERE-Klausel vorhanden und korrekt ist!

Praxis 7 · Bonus (+5 Punkte)

Zusatzaufgabe: SQL Stored Functions

🧠

In der Klausur 2026 gab es 5 optionale Zusatzpunkte für das Erstellen einer benutzerdefinierten Funktion in SQL (Stored Function). Sie liefert immer genau einen skalaren Rückgabewert.

Struktur & Delimiter-Umschaltung

13.1 · DELIMITERDa innerhalb der Funktion Semikolons verwendet werden, muss der Befehlstrenner temporär umgestellt werden (z. B. auf //).
13.2 · DETERMINISTICSignalisiert dem Query-Optimizer, dass die Funktion bei gleichen Eingabeparametern immer dasselbe Ergebnis liefert.
▸ Vollständige Schablone: Rabatt-Berechnung
DELIMITER //

CREATE FUNCTION berechne_gebuehr (basispreis DECIMAL(8,2), ist_premium BOOLEAN)
RETURNS DECIMAL(8,2)
DETERMINISTIC
BEGIN
    DECLARE endpreis DECIMAL(8,2);
    
    IF ist_premium THEN
        SET endpreis = basispreis * 0.80; -- 20% Rabatt
    ELSE
        SET endpreis = basispreis;
    END IF;
    
    RETURN endpreis;
END //

DELIMITER ;

-- Aufruf in normalem SELECT:
SELECT titel, preis, berechne_gebuehr(preis, TRUE) AS rabattpreis FROM filme;
